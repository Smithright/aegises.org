The case

Standardize the control contract. Keep every product replaceable.

We treat this as an operating-model problem before it becomes a product-selection problem. The enterprise needs stable responsibilities and contracts; the technologies underneath them should stay swappable.

Five responsibilities make up the contract: identity, policy, capability, observability and evidence. Fix those, and organizations remain free to choose the products that implement each one — cloud by cloud, region by region, decade by decade.

FIXED FOR TEN YEARS

Responsibilities · interfaces · evidence schema · the runtime path

CHOSEN PER CONTEXT

Policy engine · gateway · runtime · mesh · store · model

What this buys the CIO: the ability to change any single product in the stack without renegotiating the security posture of everything above it.

What the architecture optimizes for

Every action crosses an explicit control boundary.

Permissions can narrow through delegation but never silently widen.

Services are discovered by capability and policy context — not hard-coded endpoints alone.

Operations hold health, version, ownership, evidence and an off switch in one place.

Existing enterprise investments are reused wherever they satisfy the responsibility.

The unfamiliar one

A grant is not a role

A role describes what an actor is, and persists. A grant describes what an actor may do — bound to an audience, an action, a scope and an expiry — and is designed to die.

Four properties we require of every grant:

→ Audience-bound — usable only at the intended resource

→ Attenuable — a holder can narrow it, never widen it

→ Short-lived — expiry is the default revocation mechanism

→ Verifiable offline — routine work does not need a round trip

Design tension we will resolve in week 4, together: offline verification gives you latency; online decisions give you instant revocation. High-risk actions get the round trip. Routine actions get local verification with a short TTL. Where [CLIENT] draws that line is a governance decision, not an engineering one.

Reference architecture · runtime model

Every consequential call follows one explainable path.

Implementation varies by risk tier. The logical sequence does not — it stays legible to engineers, operators, security and auditors alike.

1
Express intent

A human, workflow or agent requests a capability — not an endpoint.

2
Establish identity

Resolve human, workload, agent type and delegated authority.

3
Discover

Find eligible services by capability, locality, health, cost, version.

4
Decide policy

Actor, action, resource, context, risk, breaker state, delegation limits.

5
Convey authority

Issue a short-lived grant bound to audience, action, scope and expiry.

6
Enforce

The mediation boundary verifies the grant and exposes only approved interfaces.

7
Execute

Run locally, at the edge or in cluster with the required isolation and limits.

8
Produce evidence

Correlate decision, grant, version, runtime, output, side effects, outcome.

02
Reference architecture · north star

Shared semantics are the destination, never the prerequisite.

The control plane answers "may this actor perform this action?" The knowledge plane answers "what does this request mean, what should the actor know, and which evidence supports the result?" Keeping them distinct is what stops a vector store from quietly becoming an authorization layer.

In POC scope

Minimum viable implementation

Catalog metadata, schemas, curated retrieval sources and explicit provenance. Memory stays narrow, task-bound and disposable. Enough to prove governed invocation without making an ontology programme a dependency.

Beyond POC

North-star implementation

A federated enterprise ontology connecting business concepts, service capabilities, policies, data products, owners and evidence. Agents request meaning and capability rather than vendor endpoints, and receive context appropriate to identity, task and risk tier.

STAGE 1

Cataloged

Named services, schemas, owners, classifications and approved sources.

STAGE 2

Semantically connected

Shared vocabulary, entity resolution, provenance and relationship-aware retrieval.

STAGE 3

Governed organizational memory

Policy-aware context, reusable knowledge products, feedback loops, measured grounding quality.

The critical separation. Ontology describes meaning. Policy determines authority. Retrieval supplies evidence. Models generate or choose actions. Combine these into one opaque "AI layer" and you create an assurance problem that no dashboard can repair afterwards.

02
Reference architecture · cross-cutting

Telemetry is what you collect. Evidence is what survives an auditor.

One invocation context is carried through policy, routing, runtime and backend. That single correlation is the difference between a dashboard and a defensible answer.

The contract

A single OpenTelemetry context propagates from intent through decision, grant, enforcement, execution and outcome. Vendor-neutral by design, so the backend stays replaceable.

Emitted by the boundary — not by your service teams. Adopting the golden path means inheriting the instrumentation, not writing it.

Governed reaction

Telemetry may trigger automation — scaling, remediation, approvals, breaker trips. But the reaction is itself an action, and crosses the same control boundary as any other.

An auto-remediation with ambient authority is just a faster incident.

Questions this makes answerable

Which human does this action ultimately trace back to?

Which policy version permitted it, and who approved that version?

What was the grant's scope and expiry at the moment of use?

Which service version and runtime actually executed it?

What side effects occurred, and are they reversible?

Were there attempts on this path that were denied — and why?

If we revoke now, how long until the last valid grant expires?

02
Reference architecture · non-goals

What we are deliberately not doing.

Stated up front, so nobody has to discover it in week seven. Each of these is a way this class of programme reliably fails.

Not doing 01

A universal ontology as a prerequisite

Shared semantics grow where they materially improve discovery, policy, interoperability or assurance — bounded domain first, never enterprise-first.

Not doing 02

Rewriting services in WebAssembly

Portable mediation is a useful boundary pattern where the host interface matters. It is not dogma, and it is not a migration programme.

Not doing 03

One synchronous policy service in every request path

That is an availability incident waiting for a Tuesday. Risk tiering plus local verification with short TTLs keeps the hot path fast.

Not doing 04

A parallel identity, secrets or logging estate for agents

Agents are a new class of actor inside the platform you already operate — not a new platform beside it.

Not doing 05

A model-autonomy showcase

The demonstration is the control path and the evidence record. Impressive agent behaviour is not the deliverable and will not be scored.

Not doing 06

Replacing your gateway, SIEM or identity provider

If an incumbent satisfies the responsibility, it stays. We are adding a contract, not an estate.

Lane · data governance & data engineering

A classification you cannot enforce at access time is a label, not a control.

This is the first place in the estate where the label becomes enforceable — and the last place anyone should build a shadow data programme.

Data governance & risk

Classification becomes an input to the policy decision — actor, action, resource and data class, evaluated at the moment of access rather than asserted in a catalog.

Purpose limitation becomes expressible. A grant carries the purpose it was issued for; using it for another purpose is a denial, and the denial is evidence.

Memory is a governed service, not a transcript dump. Narrow by default, task-bound, disposable, with retention and deletion semantics you define.

Provenance is mandatory, not optional. Source identity, timestamp and ownership travel with every retrieved fact.

We need from you: the data classes in scope for the first path, their owners, and the one class that is categorically out of bounds — by week 1.

Data engineering

No new pipelines in this proof of concept. Curated existing sources only. If it needs an ingestion project, it is out of scope by definition.

Retrieval is evidence, never authorization. Access filtering happens in the control plane; the retrieval layer is never asked to be a security boundary.

Data products gain a capability contract — what it answers, freshness, owner, classification, policy context — reusing your catalog, not replacing it.

Grounding quality is measured, not asserted. Citation coverage and source freshness are instrumented from week 6.

We need from you: read access to the catalog, one named data engineer at 0.5 day/week, and the freshness SLA of the sources the first path depends on.

A2
Appendix · vocabulary

Six terms this deck uses precisely.

Each is commonly used loosely. Where a definitional argument starts, it usually ends here.

Ambient authority

Permission an actor holds by virtue of where it is running rather than by an explicit, attributable grant. A long-lived service-account key on a pod is ambient authority. It is the default state of most estates and the thing this architecture exists to remove.

Capability grant

A short-lived, audience-bound, attenuable credential conveying a specific authorization decision to the point that enforces it. Distinct from a role, which describes what an actor is and persists indefinitely.

Attenuation

The property that a holder of authority can pass on a narrower version of it and never a wider one. This is what makes multi-agent delegation governable rather than merely observable.

Mediation boundary

The enforcement point that verifies a grant and exposes only the approved interfaces of a resource. May be a sidecar, a gateway plugin, a portable runtime or a native component — the pattern is fixed, the implementation is not.

Golden path

The supported, templated, instrumented route by which a team registers and operates a capability. Its quality is measured by adoption without its authors present — success criterion 7.

Evidence

Telemetry correlated well enough to answer a question under adversarial scrutiny. Distinct from logs, which are what you have, and dashboards, which are what you look at.
