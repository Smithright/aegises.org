The fabric · moves risk-per-capability and time-to-capability

One event spine returns three payoffs from a single investment — which is why it is funded once, not three times.

Most enterprises fund observability and eventing separately, out of different budgets, and build the same spine twice. Unify it once and agents become possible almost as a side effect.

The single investment

A unified event plane

One context propagated through every call. One bus. One schema for what happened, who asked, what was decided and what changed.

Built on what you run. Your existing bus, your existing observability backend. We add conventions, not infrastructure.

In POC scope
Payoff 01

Extensible observability

Every agent, service and decision on one correlated trace. New capabilities inherit instrumentation instead of adding a monitoring backlog item.

Who wins: platform, SRE, and every team that would otherwise be told to "add logging".

Payoff 02

Agent triggers

Work starts because something happened — a PR opened, a ticket raised, a threshold crossed — not because a human remembered to ask.

Who wins: AI practice and the business. An agent that can only be called is a tool; one that can be triggered is a colleague.

Payoff 03

Evidence as exhaust

The record auditors want is produced by the running system, continuously, rather than assembled by analysts before a review.

Who wins: governance, risk and audit — see the maturity path on slide 18.

The honest trade-off: one spine means one thing to get right. It needs schema discipline, back-pressure handling and an owner. We would rather you run one spine well than three badly — but it is a real commitment, and the platform team should hear that from us rather than discover it in month four.

The fabric · moves risk-per-capability

Capability sandboxing is why you can let agents act, not just read.

Most enterprises keep agents read-only because the only way to let one act has been to hand it a credential — and a handed-over credential cannot be bounded afterwards. This removes that trade.

Without it

The agent holds a credential

It can reach anything that credential can reach — including things nobody thought about when it was issued.

Blast radius is whatever the credential allows, so the safe answer is always read-only.

A prompt-injected or simply mistaken agent has the same reach as a correct one.

Every new action needs a fresh review, because there is no boundary to reason about — only intentions.

Net effect: the organisation says no, and calls it governance.

With WASI capability sandboxing

The agent holds only declared doors

It runs inside a sandbox where only the capabilities it declared exist at all — no ambient filesystem, network or credential.

Blast radius is the declaration, which is readable, reviewable and diffable in a pull request.

An injected or mistaken agent still cannot reach what was never wired to it.

New actions are a change to a manifest, reviewed like code — not a new security engagement.

Net effect: the organisation can say yes to writes, with a bounded answer to "what could this possibly do?"

The honest trade-off: the WASI toolchain is younger than containers, and not every workload compiles cleanly to it. We use it where the boundary earns its keep — agent tool execution — and ordinary containers everywhere else. This is a pattern, not a migration.

What this unlocks commercially: tier-1 and tier-2 write actions ship on the paved road with a manifest review, instead of queueing for a bespoke security assessment. That queue is usually the single largest source of delay between a working agent and a useful one.

The fabric · moves reuse rate

Shared vocabulary is what turns compliance and integration from projects into properties.

Two of the most expensive recurring costs in a large enterprise have the same root cause: nothing agrees on what things are called. The operating model fixes that incrementally, as a by-product of registering capabilities.

Payoff 01

Agile compliance

When a capability declares what it does, to which entities, under which classification — and the event plane records every use — a control question becomes a query rather than a project.

→ Controls are evidenced continuously, not reconstructed quarterly

→ A new regulation maps to existing declarations instead of a discovery exercise

→ Risk reviews shift from interviewing teams to reading the record

Measured as: analyst-days per control cycle, and time to answer a novel regulatory question.

Payoff 02

Cross-functional integration

When capabilities are described in business terms rather than endpoints, teams compose them without meeting first. The vocabulary becomes the integration layer.

→ An agent asks for a capability, not a system — so ownership can change underneath

→ Point-to-point integrations stop multiplying with every new consumer

→ Teams discover existing capability instead of rebuilding it in a different silo

Measured as: integrations avoided, and reuse rate of registered capabilities.

Sequencing, stated plainly, because this is where these programmes die: we are not starting an ontology programme. In the twelve weeks we do provenance and grounded retrieval only — every answer carries its source, timestamp and owner. Vocabulary grows one domain at a time, where it earns its keep, and every capability registered on the paved road contributes to it at no extra cost. If [CLIENT] has an ontology or data-mesh programme in flight, this feeds it rather than competing with it.

The path · sequencing logic

The order is not a preference — each step removes the constraint on the next.

1

Name things

Identity and the capability registry. Every capability gets an owner, a tier, a schema and a version.

Removes the constraint: you cannot grant authority to something you cannot name, and you cannot measure a portfolio you cannot list.

2

Make it visible

The event plane. One correlated context across agents and services, carrying both telemetry and triggers.

Removes the constraint: improvement cannot be claimed without a baseline carrier, and triggers cannot exist without the spine.

3

Make writes safe

Capability grants and sandboxed execution. Authority that expires, inside a boundary that is declared.

Removes the constraint: writes need both an expiring authority and a bounded runtime — and both need step one to know who is asking.

4

Pave the road

Templates, policy inheritance, tests, dashboards and documentation, encoding what steps one to three proved.

Removes the constraint: the next squad no longer needs us — which is the only definition of success that survives our departure.

WHAT BREAKS IF YOU REORDER — THE REASON THIS IS NOT NEGOTIABLE ON PREFERENCE ALONE

Tempting reorderWhy it is temptingWhat actually happens
Paved road firstIt is the visible deliverable, and platform teams ask for it.Templates can only encode conventions that already exist. Build the road first and you template guesses — then every squad inherits those guesses, and unpicking them costs more than the road saved.
Sandboxing firstIt looks like the safety-critical piece, so it feels responsible.A sandbox with nothing to grant to is a container with extra steps. Isolation without an authority model bounds the runtime but not the permission — which is the part that actually goes wrong.
Event plane lastIt reads as observability, which sounds like a phase-two concern.You lose the baseline. Improvement claimed without a pre-measured baseline is unfalsifiable, and gate 2 becomes a matter of opinion rather than evidence.
Business capability firstIt is the one the board asked about.You learn the fabric and an unfamiliar business domain simultaneously, with customer exposure. That is how twelve weeks becomes twenty — and the failure gets attributed to the architecture rather than the sequencing.

The question worth asking us: is there a constraint in [CLIENT]'s environment that forces a different order? A long identity-provider change window, for example, sometimes genuinely requires splitting step one. We would rather redesign the sequence in week zero than discover the constraint in week four.

Appendix · the control contract

Five responsibilities, four of which you already have.

Standardize these; keep every product underneath them replaceable. The one that is usually genuinely new is capability grants.

ResponsibilityAnswersIn estate?
Identity

Actor × action × resource × context		May this actor perform this action, right now?Extend

A grant is not a role

A role describes what an actor is, and persists. A grant describes what an actor may do — bound to audience, action, scope and expiry — and is designed to die.

→ Audience-bound — usable only at the intended resource

→ Attenuable — a holder can narrow it, never widen it

→ Short-lived — expiry is the default revocation mechanism

→ Verifiable offline — routine work needs no round trip

The design tension, resolved in week 4: offline verification gives you latency; online decisions give you instant revocation. High-risk actions get the round trip; routine actions get local verification with a short TTL. Where [CLIENT] draws that line is a governance decision, not an engineering one.

Appendix · runtime model in full

Eight steps, and the record they produce.

Implementation varies by risk tier; the logical sequence does not. Steps 4 and 5 are the crux — the decision, and the conveyance of that decision.

1
Express intent

A human, workflow, event or agent requests a capability — not an endpoint.

2
Establish identity

Resolve human, workload, agent type and delegated authority.

3
Discover

Find eligible services by capability, locality, health, cost, version.

4
Decide policy

Actor, action, resource, context, risk, breaker state, delegation limits.

5
Convey authority

Issue a short-lived grant bound to audience, action, scope and expiry.

6
Enforce

The sandbox verifies the grant and exposes only declared capabilities.

7
Execute

Run with the isolation and limits the risk tier requires.

8
Produce evidence

Correlate decision, grant, version, runtime, side effects, outcome.

Appendix · invariants

Five invariants, each with a test we run in week nine.

Principles are cheap; principles with a stated test are an engineering commitment. Your security and SRE teams are invited to design the adversarial cases.

InvariantWhat it meansHow you test it — and what a pass looks like
1Authority is explicitNo ambient access. Every action attributable to an identity and a decision.Pick any action from the last 24 hours at random. Produce actor, human principal, decision, grant and expiry in under 60 seconds, without asking an engineer.
2Delegation only narrowsSub-agents receive subsets of authority — never amplification.Have a sub-agent attempt an action its parent could not perform. It must fail closed, and the denial must appear in evidence with the attenuation reason.
3Execution is boundedThe capability manifest is the blast radius, and it is reviewable.Attempt an action outside the declared manifest — a network egress or file read never wired in. It must be impossible, not merely refused.
4Everything is observablePolicy, routing, runtime and business outcome share one correlated context.One trace identifier joins intent → decision → grant → runtime → backend → outcome across at least three systems, with no manual stitching.
5Technology is replaceableInterfaces and responsibilities standardized; products chosen by context.Swap the policy engine — or the gateway — behind the same contract. Zero service code changes, and evidence continuity preserved across the swap.

Open invitation: your security and SRE teams design the adversarial cases for tests 2, 3 and 5. We would rather be broken by you in week nine than by an incident in month nine. If you want a sixth invariant, we will add it.

A9
Appendix · vocabulary

Six terms this deck uses precisely.

Each is commonly used loosely. Where a definitional argument starts, it usually ends here.

Agent fabric

The shared substrate that makes the second, tenth and hundredth agent cheap to build and safe to run: registry, orchestration, delegation, identity, policy, event spine and paved road. Distinct from any individual agent.

Capability

A named, owned, tiered thing an agent or service can do, described in business terms rather than as an endpoint. The unit of registration, of policy and of reuse.

Capability grant

A short-lived, audience-bound, attenuable credential conveying a specific authorization decision to the point that enforces it. Distinct from a role, which describes what an actor is and persists indefinitely.

Capability manifest

The declaration of exactly which doors an agent's sandbox opens — network, filesystem, credentials. Reviewed and diffed like code; it is the blast radius.

Event plane

One spine carrying both telemetry and triggers, so observability, agent activation and evidence come from a single investment rather than three.

Paved road

The supported, templated, instrumented route by which a team registers and operates a capability. Its quality is measured by adoption without its authors present.
