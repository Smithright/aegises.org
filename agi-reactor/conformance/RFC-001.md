# RFC-001 — An accepted effect, a dead worker, an UNKNOWN backup

Status: executable reference specimen · 14 September 2026 · Draft 1.1 companion.

## Question

Can a recovered controller avoid repeating a non-idempotent external effect when its restored operation record cannot establish whether the effect happened?

The required outcome is **one effect and an honestly unresolved commitment**. Silently treating the operation as successful would be as incorrect as retrying it. Liveness is intentionally sacrificed for the affected step until admissible evidence resolves the uncertainty.

## System under test and limits

The supplied reference guard uses Python's standard library, a real loopback HTTP target, an actual worker subprocess, SQLite transactions and the SQLite backup API. The target commits an append to its own ledger before returning HTTP 200. The worker reads that response, then terminates with exit code 86 before saving success.

The target implements neither an idempotency key nor a status route. Each POST appends another record. Only the test oracle reads the target ledger to count effects; the recovering guard never receives that path or a query capability. Oracle knowledge must not become production evidence.

This is a small, single-controller reference implementation for falsifying a recovery algorithm. It does not exercise NATS, PostgreSQL, concurrent admission, distributed custody, real authentication, actual sandbox containment, provider behavior, multi-host failure or production deployment. The local epoch file represents recovery authority outside the restored database; it is not a production implementation of that authority. Its persistence, monotonicity and exclusion of old processes remain deployment obligations.

## Fixed input

```json
{
  "ticket": "ticket-001",
  "assignee": "agent-a",
  "step": "ticket-001/step-1",
  "operation": "operation-001",
  "epoch": 1,
  "intent": {
    "tenant": "specimen",
    "caller": "agent-a",
    "method": "append",
    "target": "local-receipt-ledger",
    "arguments": {"receipt": "R-001"}
  }
}
```

The operation binds a SHA-256 digest of canonical JSON: sorted keys, compact separators, UTF-8. This fixture uses only strings and objects; general cross-language canonicalization is not specified by this example. A unique workflow-step binding prevents replacement operation IDs from evading unresolved work.

## Fault schedule

| Step | Action | Controller knowledge | External reality |
|---|---|---|---|
| 0 | Persist ticket, step and immutable operation binding | ADMITTED; epoch 1 | No effect |
| 1 | Commit conservative send-intent before issuing POST | UNKNOWN: the call may be sent | No effect yet |
| 2 | Target commits receipt R-001 and returns HTTP 200 | Worker receives 200; durable record still UNKNOWN | Exactly one effect |
| 3 | Terminate worker with exit code 86 before result commit | UNKNOWN; no durable success evidence | Exactly one effect |
| 4 | Take a control database backup while UNKNOWN; attempt retry | Retry returns OUTCOME_UNKNOWN | Exactly one effect |
| 5 | Restore that backup; establish epoch 2 and an admission hold outside restored state | Ticket NEEDS_RECONCILIATION; operation UNKNOWN | Target ledger is not restored |
| 6 | Retry from epoch 1 | STALE_EPOCH | No new effect |
| 7 | Change the arguments, invent a replacement ID, and replay the original | INTENT_MISMATCH; RECOVERY_HOLD; RECOVERY_HOLD | No new effect |
| 8 | Test-only probe: remove global hold without changing UNKNOWN | Original → OUTCOME_UNKNOWN; replacement → STEP_ALREADY_HAS_OPERATION | No new effect |
| 9 | Inspect the test-only oracle | Guard still knows UNKNOWN | Exactly one effect; zero duplicates |

Step 8 isolates the per-operation guard so a global hold cannot mask a broken UNKNOWN check. The harness directly removes that hold; it does not implement or qualify the production barrier-release policy.

UNKNOWN starts before send because no atomic transaction spans the control database and the external target. A crash before transmission may therefore also produce uncertainty. The runtime must not silently reinterpret UNKNOWN as “sent,” “failed,” or “safe to retry.”

The trace restores the control database without restarting the target or rolling back its effect. It models the asymmetric restoration boundary, not a full infrastructure disaster. A backup predating the operation's existence, lost revocations, concurrent old/new controllers and transfer of adapter custody need additional deployment specimens.

## Assertions

- Initial execution actually reaches the target: effect count before restore is exactly 1. “Never send anything” cannot pass.
- Worker exit is 86, reached only after reading HTTP 200; the backup contains UNKNOWN.
- Guarded restore leaves the operation UNKNOWN and the ticket NEEDS_RECONCILIATION.
- Old-epoch, changed-intent, replacement-ID and same-operation requests cannot produce a new effect under the hold.
- The independent target oracle counts exactly 1 effect after recovery attempts.
- No success result or settled outcome is inferred from the oracle by the guard.

## Negative control: make the algorithm fail

The `unsafe-reset-on-restore` mode deliberately converts UNKNOWN to ADMITTED and clears the recovery hold. Replaying the original operation then creates a second external receipt.

The very same target-count assertion must fail. This control demonstrates sensitivity to the identified defect; it does not prove completeness against every recovery defect. The normal test suite expects and catches that assertion failure, so both suite tests pass when the test oracle works.

```sh
python3 -m unittest discover -s agi-reactor/conformance -v
python3 agi-reactor/conformance/unknown_restore.py --assert-safe
python3 agi-reactor/conformance/unknown_restore.py --mode unsafe-reset-on-restore --assert-safe
```

The last command is expected to exit 1 with `duplicate external effect after UNKNOWN restore`. It is an intentionally failing specimen, not a production mode. All runs use an automatically allocated loopback port and disposable local state. No third-party target or real customer operation is contacted.

## Operator contract: uncertainty is a working state

A blocked operation must expose, together: ticket and step, immutable operation identity, original initiating principal, current assignee/reconciliation owner, last admitted intent, last trustworthy evidence and time, why the outcome is unknown, next inspection action and escalation deadline. The system must distinguish an assigned operator from an actually delivered alert; notice delivery and acknowledgment are recorded independently.

The safe surface offers **inspect evidence**, **assign reconciliation**, **record a finding**, and **escalate**. It does not offer an ordinary Retry button for an unresolved non-repeatable effect. Repeated alerts are bounded and have an escalation owner. Deleting or dismissing an alert does not clear the operation hold.

A finding must preserve source, scope, observer and observation time. A separately authorized reconciliation operation can record confirmed success or confirmed absence only under the adapter's declared evidence rules. “No record found” is not proof of absence when the provider can still commit a delayed request or its observation is incomplete. If a target cannot establish final absence, the operation stays unresolved. An authorized risk acceptance for a fresh action is a distinct decision and operation, linked to the unresolved predecessor; it cannot be reported as a safe automatic retry or erase duplicate risk.

Cancellation blocks new work but cannot unsend an accepted effect. Closure may record accepted uncertainty; it must retain the unresolved effect and its audit trail. In this specimen no admissible target evidence reaches the controller, so the correct terminal observation is still UNKNOWN.

## Adjacent review requirements

1. **Compositor non-escalation.** A deployment qualification vector must plant grant-widening instructions in a permitted wiki object and a derived summary. Execute the resulting grant-change request through the real boundary. Assert that effective grants and external effects remain unchanged; a textual refusal is insufficient. This vector is specified, not implemented by RFC-001.
2. **Policy promotion.** A suggested lesson remains advisory until a versioned policy candidate passes typed validation, a scoped impact analysis, adversarial tests and independently authorized approval. Privilege-expanding changes require distinct author and approver identities; the same principal cannot satisfy both roles. Activation is bound to exact policy bytes and scope, with expiry where appropriate and a recoverable rollout. An LLM's recommendation and a human click are not evidence of informed review.
3. **Service split criteria.** A proposal to split the initial control service must identify measured lock/queue contention against a declared latency objective, an independently required release boundary, or a fault/trust boundary. Include the state owner, transaction boundary, migration and rollback, new failure modes and expected operational cost. An ontology heading or desire for symmetry is insufficient.
4. **Kernel growth.** A new primitive, protocol or daemon must name the consumer and invariant that existing contracts cannot satisfy. Prefer a typed object, method or projection until evidence requires another boundary.
5. **Isolation qualification.** Isolation is mandatory. Each deployment names its host/sandbox, effective privileges, egress policy and relevant escape/bypass tests. CHERI/seL4 is a candidate substrate with its own qualification obligations; drawing that label does not establish end-to-end containment.

## Evidence classification

Observed here: a real local side effect; crash after 200; backup containing UNKNOWN; guarded refusals; and a negative control that creates a duplicate and fails the assertion. These are reference-specimen results. Production controls remain Designed until the same fault schedule is exercised against the actual services with attributable receipts.

Zero observed duplicates is necessary for this specimen to pass. It is not an exactly-once guarantee for arbitrary external systems or a universal safety certificate.
